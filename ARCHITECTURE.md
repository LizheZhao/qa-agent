# Architecture

## Shared worker

The deployment unit is one immutable image containing the application and every explicitly declared,
compatible agent package. Agent and child-agent calls execute in-process. A package version change
produces a new lockfile, image, and deployment; the image digest is runtime identity. HTTP routes and
graph execution remain separate modules even though they currently share one OS process.

```text
FastAPI routes -> session contract -> executor -> registry -> startup-compiled graph
       |               |                |                       |
       |               +-> MongoDB      +-> gateway model       +-> registered tools
       |                   sessions +
       |                   session_turns
       +-> trace recorder -> execution trace store
       +-> immutable build data
```

The registry loads only manifest entrypoints. It never scans packages or directories. The deployment
manifest records architectural composition; `uv.lock` records the full dependency closure; an image
digest identifies the immutable runtime.

The routing-entry-agent design is documented in [`docs/routing-agent.md`](docs/routing-agent.md). The
router is the durable session owner and uses a narrow in-process invoker for at most one eligible child
agent per turn. Startup compiles child graphs with their independently declared tools, constructs the
restricted invoker and routing catalog, then compiles the router and freezes the complete registry.

Tools are installed as the single internal `orchestration-tools` distribution so runtime imports do
not depend on the repository working directory. It is lockfile-pinned and release-coupled to the
application initially, rather than independently selected in deployment manifests.

## Packaging layout

Every installable project has a distribution root containing `pyproject.toml`, a `src/` directory, and
a unique import package. The layers are intentionally distinct: distributions define release and
dependency boundaries, `src/` prevents accidental repository-root imports, and import packages avoid
module collisions in the shared interpreter. Agents remain separate distributions; tool families live
inside the single `orchestration_tools` import package. See
[`docs/repository-layout.md`](docs/repository-layout.md) for the complete tree and naming rules.

## Boundaries and dependency direction

Allowed dependencies are app to core/gateway, agent packages to core, gateway to LangChain/provider
schema helpers, and tests to any component. Core stays narrow. Forbidden dependencies are core to
agents/gateway, tools to agents, agents to app internals, and gateway to prompts/routing. Tool code is
owned under `packages/tools`, not agents.

A node is one graph step. A subgraph is a private nested workflow versioned with its parent agent. A
subagent is independently packaged/versioned, has typed request/result contracts, tool permissions,
and trace identity, even when invoked in-process. A tool is a typed domain operation; ordinary helpers
are not tools.

Application-owned conversation persistence is an infrastructure concern and implements the narrow
`SessionStore` contract under `agentic_orchestration.sessions`. Agents receive rehydrated message state
and never connect to MongoDB. Domain data follows the separate boundary `agents -> registered tools ->
API service clients -> API services -> stores`; session storage does not authorize tools or agents to
bypass that boundary.

External connection construction lives in the top-level `src/integrations` package beside
`src/agentic_orchestration`. Integrations accept explicit connection values and do not import application
settings or session contracts; the application lifespan maps its typed settings into those constructors.

## Durable conversation sessions

MongoDB stores one metadata document per session in `sessions` and one immutable document per successful
turn in `session_turns`. The controlled document and message shapes, collection names, and index names
live in `sessions/schema.py`. Session documents include nullable `tenant_id` and `user_id` fields for
future authentication, an agent ID, timestamps, status, and a monotonically increasing revision.

A turn contains the accepted user message, every message generated by that invocation in order, an
explicit final-assistant message ID, the execution trace ID, and the controlled routing outcome and
selected-child identity. Router-owned turn documents use schema version 2. Pre-router version 1 turns
are intentionally incompatible and may be removed because this service has not entered production;
router-era version 1 turns that already contain routing fields remain readable. Future persistent-schema
changes require either a compatible reader or an explicit migration.
The application-owned codec preserves supported LangChain message content, tool calls, invalid tool
calls, tool-call IDs, tool status/artifacts that are already BSON-safe, response metadata, and usage
metadata. It does not pickle Python objects. The most recent selected child is supplied to the router as
an affinity hint for contextual follow-ups; the session's owning agent remains the router.

For a normal request, a per-session process-local lock serializes load, graph invocation, and commit.
The graph invocation runs outside a database transaction. After a successful invocation, one short
MongoDB transaction inserts the next turn and advances the session only when its revision still matches
the loaded snapshot. The unique `(session_id, turn_number)` index is an independent correctness guard
across replicas. Transactions use snapshot read concern and majority write concern. A conflict aborts
the transaction and is returned without automatically reinvoking tools or the model.

New session IDs are generated by the server. The session and first turn are created in the same
transaction, so a failed first invocation leaves no empty durable session. Later failed invocations do
not alter prior history. Loading a session verifies contiguous turns through the committed revision.
The history API uses turn boundaries and `final_message_id` to expose only user/final-assistant pairs.

Conversation history remains distinct from LangGraph checkpoints. Pause-capable child graphs use the
durable checkpoint and pending-run boundary described in
[`docs/graph-interrupt-resume.md`](docs/graph-interrupt-resume.md); the router and ordinary completed
turns do not. No deployed child currently activates that path. Summaries, context compaction, and large
artifacts such as DataFrames remain future derived storage concerns; raw successful turns remain the
durable source of truth.

## Runtime lifecycle and testing

Production startup builds one asynchronous MongoDB client from typed application settings and verifies
connectivity. Session collections and their unique turn index initialize critically, and the service
fails rather than falling back to process memory when conversation storage is unavailable.
Observability collections and indexes initialize best effort and report degradation independently. The
client is registered for cleanup immediately after construction and closes on normal shutdown or any
later startup failure.

Deterministic unit and API tests explicitly inject `MemorySessionStore`, which implements the same
revisioned commit contract without network access. The memory store is a test adapter, not runtime
durability or a fallback mode.

## Execution observability

The framework now defines versioned graph, trace, span, captured-content, status, and live-event
contracts. The API creates one root trace identity per attempted turn, propagates it through router and
child graphs, returns it to the caller on success, and links it from the successful session turn. A
recorder captures turn, graph, node, model, tool, and child-agent boundaries for deterministic tests,
including parallel supersteps, loop iterations, controlled inputs/outputs, and terminal failed attempts.
Runtime causal predecessors are resolved from compiled graph edges and the predecessor node instances
that actually executed; LangGraph trigger channel names remain diagnostic attributes only.

Callbacks emit ephemeral lifecycle events into a publisher seam and enqueue ordered snapshots without
waiting on MongoDB. Production currently uses a null event publisher until the authenticated SSE
transport exists. A bounded writer persists monotonic trace/span batches and flushes best-effort at
turn completion; observability failure does not fail an otherwise committed conversation. The MongoDB
adapter and indexes have been exercised by retained scripted and live-gateway end-to-end turns. The
remaining design adds authenticated hydration plus best-effort live SSE delivery.
Request cancellation before a turn commit terminalizes open work as cancelled and releases its writer.
Cancellation after a successful commit finishes the trace as completed so conversation and diagnostic
state agree.
Authentication and tenant/session authorization are prerequisites for production diagnostic access. See
[`docs/execution-observability.md`](docs/execution-observability.md) for the storage, API, and UI
contract.

## Internal diagnostic UI

The repository will contain one internal React, TypeScript, and Vite frontend under top-level
`frontend/`. Vite's generated `frontend/dist/` assets are ignored source artifacts and will be served by
FastAPI at `/diagnostics`, allowing the built UI and orchestration API to run from one Uvicorn process.
This is not the customer-facing product frontend, which will be developed in a separate repository.

Diagnostic reads use a dedicated query boundary rather than expanding the critical `SessionStore`
mutation contract. The initial UI hydrates cursor-paged sessions and turns, trace/span snapshots, and
immutable graph definitions from MongoDB; best-effort live delivery follows historical hydration. See
[`docs/diagnostic-ui.md`](docs/diagnostic-ui.md) for the implementation-ready design.
